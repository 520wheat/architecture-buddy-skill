# 设计行为与失败 Prompt

## 何时加载

在 DD4 加载。用于写端到端流程和结构化失败证据，包括 timeout、disconnect、duplicate request、missing external confirmation、dependency failure 和 partial success。

## 目标

把正常路径和失败路径都写成可实现的行为说明；不把失败当成抽象术语，而是写出观察结果、恢复动作和残余风险。

## 输入

- 已确认的契约、数据和状态；
- 前一阶段输出的显式 Markdown 块；
- 当前用户的最新回复；
- 只使用显式输入。

## 执行

1. 先说明为什么现在要写行为与失败，以及回答后会影响哪个端到端流程。
2. 先写一条完整的 happy path，再写结构化失败证据。
3. 对每个指定失败类型写：触发条件、可见状态、观察结果、恢复动作、残余风险。
4. 如果某个失败暴露出架构级缺口，立即标为 `blocked` 并回退。
5. 只提出一个问题，优先问对主路径或失败优先级影响最大的那个。
6. 明确用户确认后是接受、修改还是回退。

## 输出契约

输出一个行为/失败框架，必须包含以下字段：

```text
状态：draft / blocked
已确认事实：
待确认事实：
已做决定：
受影响文件：
当前问题：<一个问题>？
确认结果：待用户确认 / 已确认 / 需修改 / 触发回退
```

每个失败项都必须有可观察结果；没有观察结果的失败说明不算完成。

## 不得做

- 不得省略任何指定失败类型；
- 不得只写抽象原则而不写观察结果；
- 不得一次问多个失败问题；
- 不得把失败语义留给实现者猜；
- 不得依赖隐藏上下文。

## 阻塞处理

如果失败语义依赖未确认的架构事实，输出 `blocked` 并回退到 architecture-buddy。若只是恢复顺序或默认重试次数未定，保留 `draft`，写明默认值与验证条件。
