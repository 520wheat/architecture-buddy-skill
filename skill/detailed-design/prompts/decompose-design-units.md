# 设计单元分解 Prompt

## 何时加载

在 DD1 加载。用于把已确认的架构模块拆成可写文档的详细设计单元，并决定单元顺序、合并或排除项。

## 目标

把架构模块映射成清晰的详细设计单元，让后续阶段能逐个写契约、状态和行为；不引入隐藏模块。

## 输入

- 已确认的架构模块、边界、约束和非目标；
- DD0 的显式输出；
- 当前用户的最新回复；
- 只使用当前会话里已经写出来的事实。

## 执行

1. 先说明为什么现在要分解单元，以及确认后会影响哪个详细设计阶段。
2. 列出已确认的模块，并按“一个职责一个单元”拆成详细设计单元。
3. 标出哪些模块必须单独成文，哪些可以合并，哪些必须排除。
4. 检查顺序是否会影响依赖、审阅或落盘顺序。
5. 如果存在架构层面的模块归属冲突，标为 `blocked` 并回退。
6. 只提出一个问题，通常是“顺序还是排除项”二选一中最关键的那个。
7. 明确用户确认后如何更新单元清单。

## 输出契约

输出一个单元清单框架，必须包含以下字段：

```text
状态：draft / blocked
已确认事实：
待确认事实：
已做决定：
受影响文件：
当前问题：<一个问题>？
确认结果：待用户确认 / 已确认 / 需修改 / 触发回退
```

单元清单必须能直接驱动后续阶段；如果不能，说明缺少的不是措辞而是架构事实。

## 不得做

- 不得创造新的架构模块；
- 不得把顺序问题误写成范围问题；
- 不得一次问多个排除项；
- 不得在模块归属未定时进入接口设计；
- 不得依赖未显式提供的历史。

## 阻塞处理

如果模块边界本身还没确认，或单元分解会改变 architecture handoff 的范围，输出 `blocked` 并回退。否则保留 `draft`，记录未决单元和默认顺序，再进入下一阶段。
