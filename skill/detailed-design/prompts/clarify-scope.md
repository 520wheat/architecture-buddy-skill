# 范围澄清 Prompt

## 何时加载

在 DD0 加载。用于校验 architecture handoff 是否完整、是否存在架构级缺口，以及当前请求是否已经能进入详细设计。若 scope 缺失、边界不明或回退路径不清晰，先停在这里。

## 目标

把输入中的架构 handoff 变成可继续的详细设计起点；只确认当前阶段必须知道的范围事实，不把隐藏上下文当输入。

## 输入

- 显式提供的 architecture file、ADR 路径、scope、confirmed boundaries、quality targets、pending facts、non-goals；
- 前一阶段输出的显式 Markdown 块；
- 当前用户的最新回复；
- 仅限这些显式材料，不使用未写出的历史对话。

## 执行

1. 先说明为什么现在要澄清范围，以及回答后会推进哪一个详细设计决定。
2. 复述已确认的范围、边界、目标和非目标；把缺失项放进“待确认事实”。
3. 检查是否存在架构级遗漏：系统边界、所有权、信任、数据流、质量目标或回退路径。
4. 如果缺口只是命名、示例或顺序，继续推进并保留为 `draft`。
5. 如果缺口会改变架构判断，立即标为 `blocked`，并回退到 architecture-buddy。
6. 只提出一个当前问题，且这个问题必须是本阶段最能减少歧义的那个。
7. 明确用户确认后如何处理：接受、修改、或阻塞回退。

## 输出契约

输出一个短的范围框架，必须包含以下字段：

```text
状态：draft / blocked
已确认事实：
待确认事实：
已做决定：
受影响文件：
当前问题：<一个问题>？
确认结果：待用户确认 / 已确认 / 需修改 / 触发回退
```

每一项都只写显式输入中能证明的内容；没有证据的事实必须写为“待确认事实”。

## 不得做

- 不得依赖隐藏上下文或未显式写出的历史；
- 不得一次问多个独立问题；
- 不得把架构级缺口伪装成细节问题；
- 不得替用户决定 scope、边界或回退路径；
- 不得在存在架构级冲突时继续推进后续阶段。

## 阻塞处理

如果缺少会改变系统边界、所有权、信任、数据流或质量目标的事实，输出 `blocked`，写明缺口和回退到 architecture-buddy 的原因，并只问一个补齐该缺口的问题。若只是非关键缺口，保留 `draft`，记录默认值与验证条件，继续下一阶段。
