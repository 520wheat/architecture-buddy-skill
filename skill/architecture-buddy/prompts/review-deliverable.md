# 正式交付审阅 Prompt

## 何时加载

在 `deliverable` 准备对外交付前加载，对应 S6；用户明确要求检查“是否是一份架构设计”时也加载。`draft` 不做完成门禁，除非用户明确要求升级为正式交付。

## 目标

检查候选文件是否是一份陌生读者可以使用和复核的正式架构设计，并指出缺失证据。该 Prompt 只审阅结构和语义证据，不自动判断方案是否适合用户，也不把关键词命中当质量通过。

## 输入

- 正式架构设计文件；
- 相关架构 ADR 和决策过程记录；
- 圆桌记录（若触发）；
- 当前场景、设计状态、用户确认项和待验证事实；
- `references/deliverable-gate.md` 以及领域透镜的适用范围。

## 审阅顺序

1. 先确认产物角色：正文是否是正式设计，ADR 是否聚焦决策，过程记录是否只是依据。
2. 检查问题/目标/约束 → 场景/流程 → 能力/边界 → 应用/集成 → 技术机制/质量属性的推导链。
3. 检查模块边界、职责、协作、数据归属、接口语义和至少一条端到端主路径。
4. 检查至少三类结构化失败证据：用户可见状态、触发条件、观察结果、恢复动作、残余风险。
5. 检查机制与策略分离、选项理由、放弃方案的代价、质量属性如何改变边界。
6. 检查演进切片是否有触发指标、改动位置、不改位置、N+1 成本、验收和回退。
7. 检查反例、领域不变量覆盖表、安全删除不变量（适用时）和关键未决策略默认。
8. 如果触发圆桌，检查提议、主持人提问、用户同意、席位匹配依据、逐席观点、实质性用户反馈、反馈影响、综合结论和正式设计/ADR 回写。
9. 对 `reference/retrospective` 单独报告已有项目的只读工程基线，不因基线缺陷自动否决候选设计。

## 输出契约

```text
交付角色检查：通过 / 不通过
架构定位与推导链：通过 / 不通过
边界、主路径与契约：通过 / 不通过
失败、安全与可观测性：通过 / 不通过
机制/策略与决策理由：通过 / 不通过
演进、N+1 与反例：通过 / 不通过
领域不变量与待验证默认：通过 / 不通过
圆桌证据与综合回写：通过 / 不通过 / 不适用

阻塞问题：
- <必须补齐才能交付的具体证据>

建议修订：
- <不阻塞但能提高可读性或可演进性的具体建议>

结论：
设计状态：draft / design-ready / blocked
是否可以宣称“架构设计已完成”：是 / 否
理由：<绑定到具体章节和证据，不使用分数或关键词作为唯一理由>
```

## 不得做

- 不得只检查标题、章节数量或关键词；
- 不得把“有圆桌”当作圆桌质量通过；
- 不得把“有模块/API/数据库”当作架构设计通过；
- 不得替用户填补未决策略或把待验证事实改成已决定；
- 不得把代码编译、空骨架或 PR Review 的缺失混同为当前架构设计门禁失败；
- 不得在存在阻塞问题时宣称设计完成。

## 阻塞处理

发现缺项时给出最小可行动补洞任务和对应证据位置。若证据依赖用户选择，标为 `blocked` 并提出一个问题；若只依赖资料或测试，标为“待验证”并写清验证条件和回退路径。
