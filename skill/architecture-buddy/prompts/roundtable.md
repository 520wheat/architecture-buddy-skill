# 圆桌 Prompt

## 何时加载

在 `deliverable` 选择主策略前发现会改变架构边界、质量属性或故障语义的高影响互斥分叉时加载，对应 S4。常见分叉包括 CP vs AP、同步 vs 异步、中央协调 vs 分布式、数据/历史模型、复杂度 vs 可运维性。

如果没有高影响分叉，不主动制造圆桌；在过程记录中写“未触发圆桌：当前没有需要多立场验证的高影响分叉”。如果用户主动要求圆桌，仍要先锁定一个决策点和席位范围。

## 目标

围绕一个决策点引入不超过三个匹配的做法透镜，先逐席呈现，再让用户给出实质性反馈，最后把冲突、选择、代价和待验证事实写回正式设计与 ADR。透镜不是名人，不是投票器，也不替用户决策。

## 输入

- 已确认的问题框架和第一性原理结果；
- 当前唯一的高影响决策点及候选方向；
- `references/lens-catalog.md` 的 `best-for` / `not-for`；
- 主包内置的 `lenses/*.md`；
- 用户是否已经同意圆桌，或任务上下文是否明确授权假设同意。

## 执行顺序

### 阶段一：提议和授权

先写清“高影响互斥分叉”和“提议圆桌”，说明为什么单一视角不足、准备邀请哪些席位。必须单独提出一行：

```text
主持人提问：<当前只需要用户回答的一个决策点>？
```

若用户尚未同意，停止加载透镜，只等待用户同意、修改问题或选择跳过。若用户明确同意，或任务上下文明确授权，记录“用户同意圆桌（任务上下文已授权）”后继续。

### 阶段二：动态选席

最多选择三席。每席必须说明它在目录中的 `best-for` 如何匹配当前分叉，以及 `not-for` 是否限制其结论。安全/信任会改变边界时邀请 `zta-resource`，或明确说明不邀请的理由。

没有匹配透镜时，明确写“无匹配透镜”，使用策略/反模式对照；不得伪造已安装席位，也不得因降级席位本身扣分。

### 阶段三：逐席讨论和用户反馈

按固定契约逐席给出观点：

```text
## Lens: <短名>
### On the decision point
### Heuristics applied
### Risks / what they'd worry about
### Would not do
### Evidence style
```

所有席位意见呈现完后，再给用户一次反馈机会。反馈必须是选择、修改、质疑、补充约束或待验证标记，不能只写“同意”。紧跟一行 `反馈影响：`，说明反馈改变、确认或标记待验证的具体选择、边界、代价、验收或演进项。

### 阶段四：综合回写

主持人综合席位冲突、适用边界、代价、证据和用户反馈。只有在反馈已经被绑定到具体设计项后，才形成综合结论。综合结论必须进入正式架构设计的决策/取舍/失败/演进章节和一个架构 ADR；圆桌记录不能成为最终交付物。

## 输出契约

```text
高影响互斥分叉：
提议圆桌：
主持人提问：<一个问题>？
用户同意圆桌：<明确同意或任务上下文授权；未同意则写等待状态并停止>
席位选择理由：
席位匹配依据：<逐席引用 lens-catalog 的 best-for / not-for>

## Lens: <短名>
### On the decision point
### Heuristics applied
### Risks / what they'd worry about
### Would not do
### Evidence style

用户反馈：
反馈影响：
主持人综合结论：
正式设计回写位置：
ADR 回写位置：
```

## 不得做

- 不得在用户尚未同意圆桌时加载席位或伪造发言；
- 不得一次讨论多个互相独立的决策点；
- 不得把席位观点数量当投票结果；
- 不得把透镜写成名人、顶级架构师或权威替身；
- 不得把用户反馈压缩成“用户同意”；
- 不得遗漏综合结论到正式设计和 ADR 的回写；
- 不得因没有匹配透镜而伪造领域证据。

## 阻塞处理

圆桌未获授权时停在提议/提问。用户反馈仍无法形成选择时，将设计标为待验证或 `blocked`，记录依赖事实、一期默认、触发条件和回退路径；不能替用户定案。
