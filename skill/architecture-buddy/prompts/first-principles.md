# 第一性原理 Prompt

## 何时加载

在问题框架得到用户确认或明确标记为可继续后加载，对应 `deliverable` 的 S1。已有项目用于 `reference/retrospective` 时也要加载，但代码只作为事实证据，不作为现成方案照抄。

## 目标

从不可再简化、可验证的事实出发重推架构方向，避免从产品名、行业惯例或“大家都用这个中间件”直接跳到方案。

## 输入

- 已确认的问题框架；
- 产品场景、约束、质量目标和已有事实；
- 相关领域透镜的核心不变量（若已匹配）；
- 用户已表达的偏好。偏好是约束或候选方向，不自动等于决定。

## 执行

1. 列出 2–4 条当前方案中的假设草案，并逐条区分“已证实、用户偏好、待验证”。
2. 询问哪些只是习惯、技术名或组织惯例；用户不知道时先替用户起草修订版本。
3. 把方案名剥掉，提取仍然成立的基本事实：失败会怎样、谁必须信任谁、信息能否丢失、状态谁拥有、延迟/成本的下限、谁负责运维。
4. 将事实分为领域不变量、质量属性约束和实现环境事实；明确每一项的证据或待验证方式。
5. 从事实推导稳定机制，再列出不超过两个策略方向。机制回答“问题类绕不开什么”，策略回答“在约束下有哪条可选路径”。
6. 对每个方向写依赖事实、主要收益、主要代价和会拒绝的反例。
7. 只提出一个当前最需要用户判断的问题；如果方向仍未能决定，保持阻塞状态。

## 输出契约

```text
假设草案：
- <假设>｜状态：已证实 / 用户偏好 / 待验证｜依据：

基本事实：
- <剥掉方案名后仍成立的事实>｜类型：领域不变量 / 质量属性 / 环境事实｜证据：

待验证事实：
- <事实>｜验证方式：<测试、资料、用户确认或运行数据>

从事实推导的机制：
- <稳定机制>：<它解决的基本问题>

策略方向（最多两个）：
- 方向 A：<路径>｜依赖事实：<...>｜收益：<...>｜代价：<...>｜拒绝的反例：<...>
- 方向 B：<路径>｜依赖事实：<...>｜收益：<...>｜代价：<...>｜拒绝的反例：<...>

主持人提问：<一个选择/补充事实/标记待验证的问题>？
回答的影响：<会改变哪一个机制、策略、边界或验收条件>
```

## 不得做

- 不得用“结果/硬约束/优化变量”三列表格冒充第一性原理；
- 不得用类比、成熟产品名称或流行模式代替基本事实；
- 不得把用户说“想用 Kafka/微服务/Agent”直接当作架构决定；
- 不得把机制和策略混在同一层，也不得为每个领域名词新增一个机制编号；
- 不得在用户没有选择或标记待验证前替用户选定策略。

## 阻塞处理

若基本事实之间冲突，先显示冲突和需要确认的质量属性；若关键事实无法验证，给出一期可逆默认、触发条件和回退路径，并将设计状态保留为 `draft` 或 `blocked`。
