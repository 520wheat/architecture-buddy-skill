# 设计与 ADR 综合 Prompt

## 何时加载

在问题类、基本事实和关键策略已经确认，或圆桌完成综合后加载，对应 `deliverable` 的 S5 和 S7。若仍有影响主干的未决选择，先回到问题澄清、第一性原理或圆桌，不得用综合阶段替用户拍板。

## 目标

把已确认的推理和决策整理成三种角色清晰的产物：正式架构设计文件、架构 ADR、决策过程记录。正式架构设计是主要交付物；过程记录不是会议纪要式最终答案。

## 输入

- 已确认的问题框架、基本事实、机制和策略；
- 圆桌过程记录及用户反馈（如触发）；
- 已确认和待验证的决策、与问题风险匹配的失败证据、演进范围和验收条件；N+1、反例、领域不变量表和复杂演进记录仅在适用时提供；
- 用户指定的文件路径、命名和工程流程；没有指定时使用清晰的 Markdown 文件名，不擅自写入项目目录。

模板：

- 正式架构设计：`templates/architecture-deliverable.md`
- 单个架构决策：`templates/adr-template.md`
- 过程与圆桌留痕：`templates/decision-record.md`

## 执行

1. 先声明场景和状态：`pre-development/design-ready`、`reference/retrospective`、`draft` 或 `blocked`，不要混淆架构完成和开发就绪。
2. 按 `templates/architecture-deliverable.md` 形成正式架构设计：以目标/背景/约束、实现原则、逻辑架构、技术选型/部署、数据治理、非功能设计六个核心板块为主；在非功能或决策章节中按风险补充失败、演进、领域不变量、N+1 和反例。
3. 按 `templates/adr-template.md` 将“为什么选这个”整理为一个或多个 ADR；每个 ADR 聚焦一个具体分叉，包含背景、选项、决定、理由、代价、风险和待验证事实。
4. 按 `templates/decision-record.md` 将讨论过程压缩为决策过程记录：问题、提议方案、用户/席位的关键观点、用户反馈及影响、主持人综合结论和回写位置。
5. 对没有用户确认的内容使用“待验证”和一期可逆默认；默认必须有理由、触发条件、回退路径和重新打开决策的条件。
6. 检查正文是陌生读者可使用的设计，而不是按发言顺序排列的会议记录。

## 输出契约

输出按三个模板分别组织，不要把三种产物混成一份发言记录：

```text
=== 正式架构设计 ===
<面向陌生读者的完整设计；这是主要交付物>

=== 架构 ADR ===
<具体决策的背景、选项、决定、理由、代价、风险和待验证事实>

=== 决策过程记录 ===
<简短记录问题、观点、用户反馈、反馈影响、综合结论和回写位置>

=== 交付状态 ===
设计状态：draft / design-ready / blocked
未决事实：
后续承接：系统架构 / 详细设计 / 空骨架需要使用的边界、契约和验收条件
```

## 不得做

- 不得编造用户没有确认的目标、约束、证据或策略决定；
- 不得用模块清单、技术栈清单或会议发言代替正式架构设计；六个核心板块必须表达目标、边界、协作和取舍；
- 不得把架构设计状态写成代码已实现、已编译或已通过 PR Review；
- 不得把 reference 项目的现状直接复制成 pre-development 设计；
- 不得为了填模板制造不适用的章节，必须说明不适用原因；
- 不得覆盖上一轮架构演进记录，变化应新建记录。

## 阻塞处理

如果关键决策尚未确认，生成可用的部分并将状态标为 `draft` 或 `blocked`；列出缺口和下一步问题，不输出“已完成”的正式结论。若只是领域事实待验证，可保留一期默认，但必须同时写验证和回退条件。
