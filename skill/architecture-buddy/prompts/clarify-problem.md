# 问题澄清 Prompt

## 何时加载

在 `deliverable` 的开始、问题类尚未锁定，或设计对象的层级和边界不清时加载。对应主流程的 S0、S2 和 S2.5。`draft` 只在当前讨论卡点需要重新界定时加载；不要为了聊天而生成完整设计框架。

## 目标

把用户的请求从“想做什么功能”澄清为一条可讨论的架构问题陈述。只推进当前最关键的一步，不把澄清变成问卷。

## 输入

- 用户当前请求和已经确认的上下文；
- 产品定稿、ADR 0000 或用户提供的约束材料；
- 若为 `reference/retrospective`：已有项目的只读事实、版本和工程基线；
- 当前模式（`draft` 或 `deliverable`）和场景（`pre-development` 或 `reference/retrospective`）。

## 执行

1. 先用一句话说明：为什么现在需要澄清，回答后将推进哪个设计决策。
2. 从已有材料中起草设计对象、核心问题类、目标、约束和非目标；不要求用户从零填写。
3. 标出当前属于哪一层：架构设计、系统设计、详细设计或其他等价层；说明适用和不适用的层及原因。
4. 写出当前推导链：问题/目标 → 场景/流程 → 能力/边界 → 应用/集成 → 技术机制/质量属性。不适用的环节写明理由。
5. 将未知事实列为“待验证”，不要把猜测写成决定。
6. 只提出一个最能改变当前边界或方向的问题；问题后说明用户回答会改变什么。

## 输出契约

输出一个短的“问题框架”，按以下顺序组织：

```text
设计对象：
当前模式/场景：
我们正在解决的问题类：
目标与质量属性：
核心约束：
明确不做：
架构定位：适用层 / 不适用层及原因
当前推导链：
待验证事实：
主持人提问：<一个问题>？
回答的影响：
```

框架不要求每一项都有最终答案；不能确定的项写“待验证”。完成后等待用户确认、修改或补充，再进入下一阶段。

## 不得做

- 不得把模块、服务、API 或技术栈清单当作问题类；
- 不得一次提出多个互相独立的问题；
- 不得逼用户选择他无法判断的内部分类；
- 不得因为输入来自已有项目就修改项目代码或把现状自动当成设计；
- 不得在问题类、目标和边界尚未确认前进入技术选型或圆桌席位讨论。

## 阻塞处理

如果缺少决定问题类所需的事实，列出缺口和一期可逆默认，并说明验证触发条件与回退路径。若用户拒绝或无法回答，保留“待验证”并只推进不依赖该事实的部分；不能替用户拍板。
