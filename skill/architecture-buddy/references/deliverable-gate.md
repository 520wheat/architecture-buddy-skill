# 完成门禁（S6）

在宣称「架构设计已完成」之前，逐项自检。任一项失败 → 继续补洞，禁止交卷。

1. 摘要能否让陌生人讲清「解决什么 / 不解决什么」
2. 是否有信任/边界与一条端到端主路径
3. 关键机制与策略是否区分；重要策略是否有为何选/不选
4. 是否有与本问题风险匹配的失败语义和可测验收句；分布式调用、状态转换、副作用或安全风险较高时，增加结构化失败表（用户可见状态、触发条件、观察结果、恢复动作、残余风险）
5. 是否说明当前范围、下一阶段和明确不做；需要演进规划时再写具体触发条件与回退
6. 正文几乎无内部黑话（M1、入口 B、S0…）
7. **变化轴 / N+1（按需）**：下一同类需求是否主要落在变化轴上？只有存在重复变体或明确扩展风险时强制写清该改什么/不该改什么
8. **反例（按需）**：只有当抽象可能吞并语义不同的问题时，写明必须拒绝的反例
9. **能力 vs 复杂度**（一句话自问）：这次是在增加可组合能力，还是只在增加缠绕复杂度？
10. **增强证据按需触发**：领域不变量覆盖表、结构化失败表、安全删除不变量、N+1、反例和详细演进记录只在领域机制或风险确实需要时加入；不适用时说明原因，不为了门禁填充。
10a. **未决策略可用默认**：关键未决策略若会阻塞当前边界，应给出一期首选默认、理由、触发条件、回退路径和重新打开条件；低影响未知项可以直接标为待验证。
11. **正式产物**：必须存在正式架构设计文件；小范围设计可以由一份架构 ADR 直接承担。会议记录和决策过程记录只能作为依据，不能替代正式设计。
12. **圆桌过程证据**：若预检识别高影响分叉，伴随记录必须保留提议、主持人提问、用户选择、席位/透镜契约、用户反馈与主持人综合结论；综合结论必须进入正式设计的决策与代价。正文仍应是架构设计，不得变成会议记录。
12a. **席位匹配依据**：每个席位是否引用 `lens-catalog` 的 best-for/不适用范围；安全/信任若会改变边界，是否说明邀请安全透镜或不邀请的理由。
12b. **实质性用户反馈**：是否记录了选择、修改、质疑、补充约束或待验证标记；单独的“用户同意”不通过。
12c. **交互与反馈回写**：是否先逐席呈现，再给用户实质性反馈机会；是否明确该反馈改变、确认或标记待验证的具体设计项；综合结论是否把每条用户反馈绑定到正式设计的选择、边界、代价、验收或演进位置。
13. **圆桌降级诚实性**：没有匹配领域透镜时，是否明确记录“无匹配透镜”并以策略/反模式对照完成同等推理；评分不得因降级席位本身扣分，但相关性、完整性和综合回写仍需满足要求。
14. **架构定位**：写明设计对象属于哪一层，以及哪些层适用或不适用；不适用必须有理由。
15. **推导链（按适用性）**：能从问题/目标和场景/流程推导到能力/边界、应用/集成和技术机制/质量属性；非业务系统用核心问题、状态不变量或资源边界替换业务词汇。
16. **系统设计边界**：服务、模块、API、数据库、消息组件或技术栈清单不能单独通过架构门禁；必须说明边界为何这样划分、质量属性如何影响取舍。下一次变化改哪里仅在有扩展风险时要求。
17. **场景与状态**：标明 `pre-development`、`reference/retrospective` 或其他场景，并标明 `draft`、`design-ready` 或 `blocked`；不能把设计讨论和开发就绪混写。
18. **后续交接**：代码系统说明后续系统架构、详细设计和空骨架需要承接的边界、契约和验收条件；当前门禁不要求真实代码、编译或 PR 入库。
19. **只读事实**：`reference/retrospective` 不得修改被测项目；已有代码、编译和部署状态作为独立基线记录。
20. **演进可追踪**：每个 Milestone 记录相对上一轮变更了什么、为何变更；新记录不得覆盖旧记录。
21. **文档角色清晰**：正式架构设计文件是当前主要成品；会议记录记录过程，架构 ADR 记录具体决策，三者不能混为一份只有发言的会议纪要。采用 Issue 流程时，架构变化使用新记录。
