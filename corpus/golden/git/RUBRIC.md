# RUBRIC — git

## 必中机制（≥5）

- 内容寻址对象库（blob / tree / commit / tag），对象由内容哈希标识
- 内容以 DAG 快照组织；相同 SHA ⇒ 相同内容，可短路比较
- 历史亦为 DAG：commit 可有零或多父；合并记录在父指针中
- refs 指向 commit（或间接指向其他 ref）；分支是轻量指针移动，不是目录拷贝
- 本地提交与向远程推送解耦：可离线 commit，再决定何时 share
- Plumbing / Porcelain 分层：底层 DAG/对象操作与面向用户的工作流命令分离
- （加分）工作区 / index（暂存区）/ 对象库三区交互；loose object 后继有 pack 压缩路径

## 必中策略分叉（≥3）

- 内容存储：DAG 快照 vs 基于 delta 的 changeset（多数传统 VCS）
- 历史形态：DAG 多父合并 vs 线性历史（SVN 等）
- 分发：分布式多仓库（本地可完整历史）vs 中央服务器必经才能「记入历史」
- （加分）工作流心智：高灵活换概念负担（commit vs push）vs 中央模型「忘记 push」更简单

## 叙事完整性

- 层 A（A1–A8）与层 B（B1–B6）齐全，封面元数据完整；B6 需包含变化轴、N+1、反例及能力/复杂度边界证据
- 主路径可走通：工作区变更 →（可选）暂存 → commit 对象入库 → 更新 ref；分享时再 push
- 硬约束动机（分布式工作流、内容完整性、高性能）在摘要或上下文中可见
- 取舍写清放弃了什么（如中央必经、纯线性历史、默认 delta 主存模型）及代价

## 幻觉黑名单（出现则 FAIL）

- 声称 Git **必须**有中央服务器才能提交 / 才能形成本地历史
- 把分支说成「必须复制整棵工作树/仓库目录」才能存在
- 声称相同内容在不同 commit 下必然有不同对象身份、无法用 SHA 短路
- 把 Git 写成只能线性历史、不能多父合并
- 把 commit 与 push 说成同一操作、不可离线增量提交
- 整段套用 CVS/SVN「一切变更必须经中央仓库才算提交」叙事而不点出分布式差异
