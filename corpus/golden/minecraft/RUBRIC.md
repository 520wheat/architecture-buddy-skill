# RUBRIC — minecraft

## 必中机制（≥5）

- 服务端权威世界状态（方块/实体/库存等）；客户端不可信
- 离散 tick 模拟循环推进规则与世界（非纯事件驱动 CRUD）
- 区块（chunk）作为空间分区与加载/同步单位
- 兴趣管理 / 视距裁剪（AOI）；非默认全图广播
- 协议化同步：意图上行、状态下行（或等价叙述）
- 客户端预测 + 与服务端和解（冲突以权威为准）
- 可模组/数据驱动扩展边界服从权威与协议兼容（不是「只讲怎么写插件」）

## 必中策略分叉（≥3）

- 单线程/单世界 tick vs 区域并行模拟（及跨区交互代价）
- 单逻辑权威服 vs 代理/群组多逻辑服扩容
- 弱预测 vs 强预测（手感 vs 和解/作弊面）
- （加分）偏数据驱动扩展 vs 深度模组/改协议；接近原版语义 vs 第三方优化服

## 叙事完整性

- 层 A（A1–A8）与层 B（B1–B5）齐全，封面元数据完整
- 主路径可走通：兴趣加载 → 意图 → tick 裁决 → 状态同步 → 和解
- 问题类定为共享体素/实体模拟，而非插件开发教程
- META 或 B1 标明：基于公开 wiki/协议/社区资料的合理重构，**非**厂商正典白皮书
- 取舍写清放弃了什么（客户端可信、全图广播、假白皮书、教程化）及代价

## 幻觉黑名单（出现则 FAIL）

- 声称存在或依据「Mojang/Microsoft 官方完整架构白皮书」作为正典（无公开出处却写成已证实）
- 把问题类写成「如何编写 Bukkit/Spigot/Paper Java 插件」为主叙事
- 声称客户端拥有权威世界 / 默认信任客户端坐标与库存结果
- 声称默认全图向所有玩家广播全部方块与实体更新且无兴趣裁剪必要
- 否认客户端预测与和解在联机手感中的角色，又同时要求「零延迟完美一致」而不给机制
- 整段套用无关微服务/CRUD 业务后端拓扑冒充共享世界模拟
