# Design §4：圆桌与架构师视角 Skill 接口

## Status

**Approved（2026-08-05）** — 依据 ADR-0002/0003/0004；调研侧用「多视角对照」证据校准行为。

## 目标

在需要取舍对照时，由 Architecture Buddy **主持** 1–3 个已安装的架构师视角 Skill，产出**并列洞见**，由用户拍板；不把圆桌做成辩论赛或替身决策。

## 何时启动圆桌

| 触发 | 行为 |
|------|------|
| 用户明确要求多视角 / 点名某架构师 | 启动；确认已安装的视角列表 |
| 共思中出现**硬分叉**（机制已清、策略互斥且影响大） | **提议**圆桌；用户同意再请席 |
| 常规澄清、单一明显策略、用户说不需要 | 不启动 |

默认席数：**2**；用户要加深时到 **3**。超过 3 先问是否收敛问题类（避免噪声）。

## 主持职责（Buddy）

1. **选题**：用一句话钉住本轮对照点（例：「PEP 用 Agent/Gateway 还是 Portal？」）
2. **请席**：按对照点选视角（见下表启发式），说明请谁、为何
3. **并行索取**：每个视角 Skill 只回答对照点，格式见「视角输出契约」
4. **合成**：一张对照表——共识 / 冲突 / 各自适用条件 / 未决问题
5. **交还主权**：明确「你可以选 A/B/混合/先验证 X」；Buddy 可给倾向理由，但标记为建议

## 视角 Skill 不做什么

- 不主持流程、不改入口模式、不擅自开 Top N
- 不伪造「我就是某某本人」；以**蒸馏出的启发式透镜**自称
- 不覆盖用户已锁定的硬约束（可指出张力）

## 视角输出契约（运行时接口）

每个视角 Skill 被调用时应能产出（Markdown 小节即可）：

```text
## Lens: <短名>
### On the decision point
<直接回答对照点，≤10 行>

### Heuristics applied
- <可复查的启发式 2–5 条>

### Risks / what they'd worry about
- …

### Would not do
- <明确不推荐的方向及原因>

### Evidence style
<偏好的证据类型：运行数据 / 论文 / 产品对照 / 组织可行性…>
```

主持合成时不得删冲突；冲突必须可见。

## 请席启发式（可演进，非封闭名单）

| 对照点类型 | 优先请…（构建期蒸馏出的席位标签示例） |
|------------|----------------------------------------|
| 分布式一致性 / 协调 | 偏严谨证明与运维代价的透镜 |
| 演进式架构 / 组织适配 | 偏四点进化与适更性的透镜 |
| 简约与可删除性 | 偏激进简化与 YAGNI 的透镜 |
| 安全 / 信任边界 | 若有安全透镜则请；否则 Buddy 用 ZTA/SAMM/ASVS 词表补位（非名人戏） |
| Agent 系统 | 用 D8/P9 词表；可请「系统思维」透镜，避免只跟一家框架 |

具体人名席位在**构建期女娲蒸馏**时锁定；本设计只规定接口与主持规则。

## 与笔记（§3）的衔接

圆桌输出进入架构笔记：

- **M8 证据**：圆桌摘要（谁、对照点、共识/冲突）
- **M5/M7**：采纳或搁置的策略及风险
- **M6**：若用户当场决策 → 写 ADR 段；若未决 → 留在未决

## 失败与降级

| 情况 | 降级 |
|------|------|
| 请求的视角未安装 | 列出已安装；提议用 Buddy 内建模式词表做「无透镜圆桌」或暂停 |
| 视角输出空泛/跑题 | 主持重问一次对照点；仍差则换席或结束圆桌 |
| 用户只要结论不要过程 | 给短对照表 + 一句建议；不强迫阅读长启发式 |

## 非目标

- 不在 v1 做自动投票或「加权融合最优解」
- 不在运行时调用女娲
- 不把圆桌做成固定三人每轮必开

## 默认锁定（无重大分歧不改）

- 硬分叉：**先提议，用户同意再请席**
- 席数：默认 **2**，上限 **3**
- 视角输出：Markdown 契约即可（v1 不做强制 JSON 字段）
