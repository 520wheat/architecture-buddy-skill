# Design §2：一次共思的主流程

## Status

Approved（2026-08-04）

## 目标

在伙伴身份下，把 A/B/C 三种入口收敛到同一套「问题类 → 机制/策略 → 笔记/模板」产出，且不替用户拍板。

## 主流程

```text
识别入口 A/B/C
    → 第一性原理共抽核心问题
    → 界定问题类
    → 问询是否 Top N 调研
         ├─ 是 → 对照调研 → 抽机制 / 策略
         └─ 否 → 轻量对照已知模式或跳过
    →（可选）圆桌：请 1–3 个架构师视角对照
    → 共写架构笔记
    → 抽象够稳时，提议沉淀为类问题模板（用户决定）
```

### 1. 识别入口

| 模式 | 信号 | 前半段重心 |
|------|------|------------|
| A | 模糊真实问题 | 多澄清：场景、约束、成功长什么样 |
| B | 已有方案 | 多审视：假设、风险、可替换策略 |
| C | 调研/抽象意图 | 较早进入问题类界定与对照设计 |

识别后向用户简短确认：「我按 B（已有方案审视）来走，可以吗？」避免猜错。

### 2. 第一性原理共抽核心问题

与用户一起压到：

- 真正要达成的结果（不是功能清单）
- 硬约束（法规、成本、时延、团队能力等不可违背项）
- 真正要优化的变量（以及明确不优化什么）

此步能力内化于 Architecture Buddy（构建期由女娲蒸馏写入），不是运行时调用女娲。

### 3. 界定问题类

用一句话回答：「我们在解决哪一类问题？」  
后续机制/策略/模板都挂在这个类上，而不是挂在某个具体产品名上。

### 4. 问询 Top N

主动问，例如：

> 这类问题市面上已有被广泛验证的产品。要不要做一轮 Top N 对照，用来抽「机制（共性）」和「策略（差异）」？

- **同意**：再约定范围（大概 N、是否限某子领域、时间盒）
- **不同意**：用双方已知模式做轻量对照，或直接进入方案共构

### 5. 可选圆桌

当出现明显取舍分歧、或用户要求多视角时：

- 请 1–3 个**已安装**的架构师视角 Skill
- 伙伴主持：并列对照，标注共识与冲突
- 用户做最终选择

### 6. 共写架构笔记

当场产出（详见 §3）：问题类、核心问题、机制、策略选项、取舍、未决点、（若做了）Top N 来源摘要。

### 7. 沉淀判断

仅当机制稳定、策略边界清晰时，**提议**写成类问题模板；是否沉淀由用户决定。

## 非目标（本流程不做）

- 不替用户选定唯一架构并宣布「就这么定了」
- 不擅自启动耗时 Top N 调研
- 不把模块拆分图当作主交付（可为笔记附录，不是中心）
