# Architecture Buddy：可交付工作流与金标校准设计

**日期：** 2026-08-05  
**状态：** Accepted  
**范围：** 改造宿主工作流，使 skill 能稳定产出「完整架构设计」；建立金标库与对内校准门；再扩库与蒸馏。  
**不在范围：** 用户对话中的考试/打分 UX；运行时女娲；第一期收齐全部经典系统金标。

---

## 1. 问题与动机

当前 Architecture Buddy 更接近「共思剧本 + M1–M9 填空」。验收（V1–V6）主要测对话模式与静态文件，**没有**「产出一份可读、可评审、可交付的架构设计」的完成门禁。

结果：流程看似跑完，交付物仍像审计备忘录；读者看不懂文件在说什么；两分钟伪完成被误当成任务完成。

根因不是「少几个透镜」，而是：

1. **Done 未定义** —— 没有双层成品标准  
2. **无交付门禁** —— 填模板即可宣称完成  
3. **无对内标尺** —— 缺少用经典架构校准 skill 质量的闭环  

本设计采用「工作流优先」：先保证能完整交卷，再用少量金标校准，再扩素材库与蒸馏。

---

## 2. 目标与成功标准

### 2.1 产品目标

Skill 作为架构共思**同事**，在用户要求完整架构设计时，产出**双层**交付物：

- **层 A（叙事）**：陌生人能看懂系统在解决什么、边界、主路径、契约、失败、演进与验收  
- **层 B（机制/策略）**：问题类抽象——基本事实、机制、策略选项与取舍（符合 ADR-0001）

### 2.2 过关标准（分阶段）

| 阶段 | 名称 | 含义 | 对象 |
|------|------|------|------|
| A | 复现校准 | 对已知正典系统，skill 能写出接近金标质量的双层文 | **skill / 维护者** |
| B | 迁移校准 | 对未见金标的系统，仍能交同质量档次的双层文 | **skill / 维护者** |

用户路径**不包含**考试话术。考试仅用于训练与证明 skill 能力。

### 2.3 总验收

1. **用户路径**：要完整架构 → 得到可读双层文，陌生人能讲清在说什么  
2. **训练路径**：种子金标上 skill 能稳定达到 RUBRIC PASS（维护者判定）  
3. **迁移路径**：对新系统仍能交双层文，且通过完成门禁 + 抽检  

---

## 3. 已锁定决策

| 点 | 决策 |
|----|------|
| 过关顺序 | 先复现校准 A，再迁移校准 B |
| 成品形态 | 叙事层 A + 机制/策略层 B，缺一不可 |
| 日常模式 | `draft`（可残缺）/ `deliverable`（完整门禁）；「做架构设计」默认后者 |
| 素材库 | 金标考卷 + 蒸馏原料（双用途） |
| 判分分层 | 日常：结构化完成清单；正式复现：对照金标+RUBRIC；迁移：清单 + 陌生读者抽检 |
| 考试归属 | **只训练/校准 skill**，不拷问用户 |
| 落地策略 | 工作流优先（方案 1）；金标工厂为 Phase 2；考试引擎嵌在构建期 |

## 4. 工作流设计

### 4.1 模式进入

| 用户意图 | 模式 |
|----------|------|
| 一起聊聊 / 拆假设 / 帮我想想 | `draft` |
| 「做一份架构设计」「完整架构」「可交付笔记」 | `deliverable` |
| 维护者跑复现校准 | `exam-reproduce`（构建期，不对用户暴露） |
| 维护者跑迁移校准 | `exam-migrate`（构建期，不对用户暴露） |

`draft` 可升级：用户说「写成完整设计」→ 切 `deliverable`，带入已有共识，不从头问卷。

### 4.2 `deliverable` 阶段门禁（S0–S7）

按序推进；可回退补洞；**未过 S6 不得宣称交付完成**。

| 阶段 | 名称 | 完成条件 |
|------|------|----------|
| S0 | 对齐意图 | 一句话锁定今天要交的架构设计对象 |
| S1 | 第一性原理 | 假设草案 → 基本事实（含待验证）→ 从事实重推方向（非结果/约束表单） |
| S2 | 问题类 | 「我们在解决___这一类问题」锁定 |
| S3 | 对照（可选） | 先问是否 Top N / 金标对照；拒绝则记录「跳过」 |
| S4 | 圆桌（可选） | 硬分叉才提议；≤3 席；用户选主策略 |
| S5 | 双层成稿 | 先层 A 后层 B，同一文件两大部分 |
| S6 | 完成门禁自检 | 清单全绿，或红项标「阻塞/待验证」且不得假装完成 |
| S7 | 交卷 | 只交可读成品；内部编号（M1…）不进正文 |

### 4.3 日常完成门禁（S6）

任一失败 → 禁止说「架构设计已完成」：

1. 摘要能否让陌生人讲清「解决什么 / 不解决什么」  
2. 是否有信任/边界与一条端到端主路径  
3. 机制与策略是否分开；策略是否有为何选/不选  
4. 是否有失败语义与可测验收句（≥3，非形容词）  
5. 是否有演进切片（现在 / 下一刀 / 明确不做）  
6. 正文几乎无内部黑话（M1、入口 B 等）  

### 4.4 `draft` 行为

只推进当前卡点；可只留假设或半页笔记；**不跑 S6**。若用户把草稿当成品，主动提醒仍在 `draft`。

### 4.5 协作身份（不变）

伙伴/同事；不替用户拍板；禁止问卷考官 UX；用户不知道时由 skill 起草假设请确认。

## 5. 双层成品骨架

权威模板：`skill/architecture-buddy/templates/architecture-deliverable.md`  
旧 `architecture-note.md`（M1–M9）降级为**内部映射**；用户可见成品不出现 M 编号。

### 5.1 封面（≤10 行）

- 标题  
- 一句话问题类  
- 已定关键决策（≤3）  
- 明确不做（≤3）  
- 模式标记：`deliverable` / 校准对象名（仅构建期文稿）  
- 待验证事实（单独一行，禁止藏进正文假装已证实）  

### 5.2 层 A — 叙事

| 节 | 必须回答 |
|----|----------|
| A1 摘要 | 解决什么、为谁、成功长什么样（≤1 屏） |
| A2 上下文与边界 | 落点与信任边界（可 mermaid） |
| A3 主路径 | 一次关键请求从进到出 |
| A4 组件与契约 | 职责、可调用关系、禁止 |
| A5 状态、失败与恢复 | 持久化、挂了怎么办、用户可见失败态 |
| A6 安全与身份 | 信任模型；不适用则写明为何 |
| A7 演进切片 | 现在 / 下一刀 / 不做 |
| A8 如何验收 | ≥3 条可测句子 |

### 5.3 层 B — 机制 / 策略

| 节 | 必须回答 |
|----|----------|
| B1 基本事实 | 剥掉方案名后仍成立；已证实 / 待验证 |
| B2 机制 | 该类问题几乎绕不开的结构 |
| B3 策略选项 | 2～3 条路径及依赖事实 |
| B4 取舍 | 为何选、明确放弃什么 |
| B5 与对照的关系 | 对照则各记一条教训；跳过则写「未对照」 |

层 B 不得只重复层 A 模块名；须用问题类语言。

### 5.4 附录（可选）

模块/包映射、ADR 索引、圆桌摘录、金标对照表（仅校准运行记录）。

## 6. 金标库与对内校准（考试 = 训练 skill）

### 6.1 边界（硬性）

| | 对内（维护者 / 构建） | 对外（用户） |
|--|----------------------|--------------|
| 复现/迁移「考试」 | 有：校准 skill、模板、透镜 | **无**：不开考、不盲写、不打分 |
| 金标 | 标尺 + 蒸馏原料 | 可选「对照成熟系统」共思 |
| 完成门禁 | RUBRIC + 金标 diff | 仅 S6 结构完整性 |

用户话术禁止出现：开考、盲写、打分、及格/不及格。

### 6.2 金标库布局

`corpus/golden/<id>/`

| 文件 | 作用 |
|------|------|
| `META.md` | 问题类、来源、许可与引用 |
| `GOLDEN.md` | 正典双层架构设计（严格按 §5） |
| `RUBRIC.md` | 必中点、常见幻觉黑名单 |
| `SOURCES.md` | 允许阅读的公开材料索引 |

`docs/survey/architecture/D*.md` 是调研摘记，**不是**金标。升格路径：

```text
survey 摘记 → 共写/审订 → GOLDEN.md + RUBRIC.md
```

校准运行记录：`corpus/runs/<date>-<id>.md`（不冒充金标）。

### 6.3 种子集（Phase 1）

1. Kafka — 日志/流式集成  
2. git — 内容寻址 + 分布式协作史  
3. Kubernetes — 声明式控制面 / 协调循环  

Hadoop、Spark、Codex、Minecraft 等属 Phase 2 扩库。

### 6.4 复现校准流程（维护者）

1. 抽题（系统 id）  
2. 用当前 skill 按 `deliverable` 产出候选（默认可读 SOURCES；严校可闭卷）  
3. 对照 GOLDEN + RUBRIC：机制/策略命中、叙事完整性、幻觉  
4. PASS / RETRY；失败则**改 skill/模板**再跑，不改用户 UX 话术凑数  
5. 记入 `corpus/runs/`  

### 6.5 迁移校准流程（维护者）

- 目标无已有 GOLDEN（或对本次校准封存）  
- 完整 `deliverable` → 双层成品  
- S6 + 陌生读者 5 分钟抽检（维护者或第二会话）  
- 可选：与最近邻金标对照，检查乱套类比  

### 6.6 用户侧如何用金标

S3 可选询问是否对照某金标/同类系统；同意则只抽机制/策略各一条教训进层 B，禁止整段抄金标叙事冒充本系统。

### 6.7 与透镜蒸馏

金标 + RUBRIC + survey → 构建期蒸馏/升级透镜与宿主启发式（ADR-0015/0016）。运行时不调用女娲。校准通过率是构建质量信号，不是用户功能。

## 7. 分期落地

### Phase 0 — 改 skill 本体（优先）

- 宿主写入 `draft`/`deliverable`、S0–S7、S6 门禁  
- 新增 `architecture-deliverable.md`；M 模板降为内部映射  
- 用真实目标（如 SRE-Buddy）人工跑一次 deliverable 验收  
- 扩展静态检查：新模板与关键标题存在  

### Phase 1 — 三种子金标 + 对内校准门

- 产出 Kafka / git / k8s 的 GOLDEN + RUBRIC  
- 编写 `docs/build/skill-calibration.md`（维护者流程）  
- 三题各至少一次维护者 PASS  

### Phase 2 — 扩库 + 蒸馏 + 迁移校准

- 扩金标（Hadoop、Spark、Codex、Minecraft…）  
- 构建期蒸馏升级透镜  
- 迁移校准与抽检  

### Phase 3 — 可选增强

- 半自动 RUBRIC 对照报告（维护者）  
- 金标版本与 skill 版本挂钩  
- 更多问题类补盲区

## 8. 明确不做

- 不把用户对话做成复现考 / 打分 / 盲写拷问  
- 不在运行时调用女娲  
- 不以模块连线图替代双层架构设计  
- 不追求 Phase 0/1 收齐全部经典项目金标  
- 不把 survey 摘记直接当 GOLDEN  
- 不替用户拍板；S6 拦半成品结构，不替用户选策略
