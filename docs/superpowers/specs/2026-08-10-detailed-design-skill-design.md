# 详细设计 Skill 设计规格

> 状态：Approved（2026-08-10）
> 主要产物：独立的 `detailed-design` Skill，以及 `architecture-buddy` 到它的显式交接流程。

## 1. 目标

为 Architecture Buddy 增加架构设计之后的下一层能力：基于 `pre-development/design-ready` 的正式架构设计和架构 ADR，协作产出面向开发实现的详细设计文档。

详细设计只补齐实现级决策，不重新做架构设计。它需要让开发者能够根据文档继续实现模块、接口、数据结构、状态机、关键流程、异常处理、并发规则、安全约束、可观测性和测试方案。

本次能力包含两个变化：

1. 新增独立的 `detailed-design` Skill，支持架构设计交接和用户直接调用。
2. 将现有 8 个架构透镜从独立发行包统一为 `architecture-buddy` 内部的 `lenses/` 资源目录。

## 2. 范围与非目标

### 2.1 本期范围

- 只支持代码系统的详细设计。
- 只承接 `pre-development/design-ready` 的架构设计。
- 输入包括正式架构设计文件、相关架构 ADR、设计范围和待验证事实。
- 输出包括详细设计总览文档和按模块拆分的详细设计文档。
- 详细设计可以在架构约束内确定实现级选择。
- 详细设计发现架构级冲突时，暂停并回退到 `architecture-buddy`。
- 复用现有圆桌主持和架构透镜机制，不新增详细设计透镜。

### 2.2 明确不做

- 不读取已有项目代码，不做 `reference/retrospective` 反向详细设计。
- 不生成代码、代码空骨架、数据库迁移或可编译实现。
- 不改变模块边界、数据归属、信任边界、一致性模型或核心质量属性。
- 不在详细设计阶段自行修改上游架构设计和架构 ADR。
- 不新增独立的 `architecture-buddy-lens-*` 安装包。
- 不把详细设计质量简化为文件存在或关键词命中。

## 3. 设计决策

### 3.1 独立 Skill，主 Skill 负责交接

`detailed-design` 作为独立 Skill，拥有自己的 Prompt、参考资料、模板和确定性校验脚本。`architecture-buddy` 保留架构设计职责，并在架构设计通过 `design-ready` 完成检查后询问用户是否继续。

选择该方案的理由：

- 详细设计与架构设计的职责和版本可以独立演进。
- 用户仍可沿着同一对话自然进入下一阶段。
- 详细设计也能从已有的正式架构设计文件直接启动。
- 架构级回退关系可以通过显式文件和交接信息表达，不依赖隐藏上下文。

### 3.2 透镜统一为主 Skill 内部资源

现有 8 个透镜保留各自的领域内容和输出契约，但从独立 Skill 包迁移到：

```text
skill/architecture-buddy/lenses/
```

主 Skill 根据决策点和 `lens-catalog` 按需读取对应文件。选择该方案的理由：

- 透镜本身不主持流程，独立安装价值有限。
- 用户只需安装一个架构 Skill。
- 领域透镜仍然按文件隔离，维护和动态选席边界不丢失。
- `detailed-design` 可以作为真正独立的功能 Skill 发布。

代价是透镜不再独立安装和独立版本化；主 Skill 版本承担透镜资源的兼容性责任。

### 3.3 详细设计采用分阶段共思

详细设计不读取架构文档后一次性生成全文，而是按设计单元逐步确认。每个阶段只推进一个当前问题，重要接口和关键实现选择在汇总前确认。

## 5. Skill 职责

### 5.1 `architecture-buddy`

继续负责：

- 问题澄清、第一性原理、架构边界和架构决策。
- 正式架构设计、架构 ADR 和决策过程记录。
- `design-ready` 完成检查。
- 设计完成后的详细设计询问和显式交接。
- 圆桌主持及架构透镜按需加载。

新增职责只有详细设计交接，不负责生成模块级实现细节。

### 5.2 `detailed-design`

负责：

- 校验架构设计输入。
- 确认详细设计范围并拆分设计单元。
- 协作设计模块职责、接口、数据、状态、流程和横切实现规则。
- 汇总测试方案和实现顺序。
- 生成详细设计总览、模块文档和架构回退项。
- 在架构级事实缺失或发生冲突时阻塞并回退。

## 6. 交接契约与入口

### 6.1 架构设计交接

当 `architecture-buddy` 完成架构设计检查并得到 `design-ready` 后，先询问用户：

> 架构设计已完成。是否继续生成面向开发实现的详细设计？

用户同意后，交接信息必须显式包含：

```text
详细设计交接
- 架构设计文件：正式架构设计文件路径
- 架构 ADR：相关 ADR 路径列表
- 设计场景：pre-development
- 设计状态：design-ready
- 详细设计范围：用户确认的模块或功能范围
- 已确认边界：模块、数据归属和信任边界
- 已确认质量目标：延迟、一致性、可用性等目标
- 待验证事实：事实、一期默认、验证条件和回退路径
- 明确不做：本次详细设计排除的范围
```

交接信息可以出现在当前消息中，也可以由用户提供等价 Markdown 文件；不得依赖未写出的对话隐式状态。

### 6.2 直接入口

用户可以直接调用 `detailed-design`，但必须提供正式架构设计文件和相关 ADR，或提供包含同等字段的交接信息。直接入口与架构交接入口使用同一套输入校验。

## 7. 详细设计流程

### DD0：输入校验

确认文件可读取、场景和状态正确、架构边界完整、ADR 可定位、范围明确。缺少非关键事实时记录待验证事实并给出一期默认；缺少架构级事实时阻塞。

### DD1：范围和设计单元

从架构模块和用户范围中划分详细设计单元，说明每个单元的职责、输入、输出、依赖和不展开原因。用户确认设计顺序后继续。

### DD2：模块和接口契约

逐个确认模块职责、允许调用方、禁止越界、对外接口、内部接口、请求/响应、错误语义、版本和幂等要求。跨模块契约进入总览文档。

### DD3：数据和状态

确认数据结构、字段约束、数据归属、生命周期、状态机、状态转换条件、并发可见性和持久化边界。不得重新决定架构层的数据归属和一致性模型。

### DD4：行为和故障

确认关键流程、时序、算法或处理步骤，并针对超时、断线、重复请求、外部确认缺失、依赖失败和部分成功定义用户可见状态、观察结果、恢复动作和残余风险。

### DD5：横切实现规则

补齐并发控制、重试、幂等、权限检查、审计、日志、指标、追踪、配置和资源限制。发生会改变架构边界或质量属性的分叉时，停止当前阶段并回退。

### DD6：测试和实施顺序

为每个模块定义单元测试、集成测试、跨模块测试和验收条件，整理实现依赖和推荐顺序。测试设计验证详细设计契约，不以实现代码替代详细设计。

### DD7：汇总和完成检查

生成总览和模块文档，检查模块覆盖、跨模块契约一致性、未决事项、架构回退项和实现顺序。只有所有阻塞项处理完，才能标记详细设计为 `design-ready`。

## 8. 输入门禁与回退

### 8.1 必须满足的输入条件

- 架构设计文件存在且可读取。
- 场景为 `pre-development`。
- 状态为 `design-ready`。
- 已明确系统边界、模块职责、接口语义和关键数据/状态契约。
- 相关架构 ADR 可定位，且不存在阻塞决策。
- 详细设计范围明确。

### 8.2 阻塞条件

以下任一条件成立时不得继续生成详细设计：

- 模块边界或职责不清。
- 数据归属不清。
- 信任边界不清。
- 核心一致性或可靠性目标不清。
- 详细设计需要改变架构 ADR。
- 详细设计范围和架构设计范围冲突。

### 8.3 回退流程

```text
暂停详细设计
    → 记录架构回退项
    → 说明冲突位置、影响和需要重新决策的内容
    → 返回 architecture-buddy
    → 更新架构设计或 ADR
    → 重新执行 DD0 输入校验
    → 恢复详细设计
```

架构回退项使用 `architecture-feedback.md` 模板，至少记录冲突事实、受影响的详细设计单元、架构层决策问题、当前阻塞状态和恢复条件。

## 9. 产物结构

详细设计输出目录为：

```text
design-output/
├── detailed-design-overview.md
└── modules/
    ├── identity-module-detailed-design.md
    └── audit-module-detailed-design.md
```

总览文档必须包含：

- 架构输入、设计范围和不做范围。
- 模块关系、设计单元索引和跨模块契约。
- 关键端到端流程和时序说明。
- 统一错误、并发、安全、审计、日志、指标和追踪规则。
- 测试策略、模块实现顺序和依赖。
- 未决事实、一期默认、验证条件和回退路径。
- 架构回退项索引。

模块文档必须包含：

- 模块职责、边界、依赖和禁止越界。
- 对外接口和内部接口。
- 请求/响应、数据结构、字段约束和错误码语义。
- 状态机、状态转换条件和不变量。
- 关键流程、时序、算法或处理步骤。
- 异常、超时、重试、幂等、并发和部分失败处理。
- 权限、审计、日志、指标、追踪和配置要求。
- 单元测试、集成测试、边界测试和可测验收条件。

模块较少时可以将内容合并为单文件，但运行时仍按总览和模块两个逻辑层组织。

## 10. 失败语义

详细设计流程至少区分以下状态：

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `draft` | 当前设计仍在讨论，不能作为实现输入 | 继续当前设计单元 |
| `blocked` | 缺少架构级事实或发生架构冲突 | 回退到 `architecture-buddy` |
| `design-ready` | 输入合法、设计单元完整、阻塞项已处理 | 可以交给开发阶段 |

超时、断线或外部确认缺失只能记录为未知态，除非已有证据证明终态。详细设计文档必须说明未知态如何观察、如何恢复以及是否允许重试。

## 11. 完成门禁与验收

### 11.1 发行结构

- 主 Skill 和详细设计 Skill 均有 `SKILL.md`。
- `architecture-buddy/lenses/` 包含 8 个领域透镜文件。
- 不存在旧的 `architecture-buddy-lens-*` 目录。
- `release-manifest.tsv` 只声明两个 Skill 包。
- README、manifest 和实际目录一致。
- 发行包不依赖 `docs/`、`corpus/` 或本机绝对路径。

### 11.2 输入与流程

- 合法的 `design-ready` 架构输入可以进入详细设计。
- `draft`、`blocked` 或缺少架构边界的输入会阻塞。
- 缺少非关键事实时会记录默认、验证条件和回退路径。
- 架构设计完成后，用户拒绝详细设计时原流程正常结束。
- 用户同意后能通过显式交接进入 `detailed-design`。
- 直接调用和交接调用使用相同的输入校验。
- 发现架构冲突时能暂停并生成架构回退项。

### 11.3 详细设计产物

- 每个架构模块都有详细设计单元，或有不展开原因。
- 每个模块都有接口、数据、状态、行为、故障和测试设计。
- 总览文档中的跨模块契约与模块文档一致。
- 所有未决事项都有一期默认、验证条件和回退路径。
- 输出文档可以交给开发人员继续实现，而不要求读取原始对话才能理解。

## 12. 后续实施边界

实施应先完成发行目录迁移，再新增 `detailed-design` Skill，最后接入两个 Skill 的交接流程和验证样例。目录迁移必须保留透镜内容和输出契约，只改变安装形态和加载路径；详细设计实现不能夹带代码生成、已有项目反向设计或新的透镜体系。
