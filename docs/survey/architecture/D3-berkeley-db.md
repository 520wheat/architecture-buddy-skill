# AOSA — Berkeley DB
- 域: D3 数据存储与查询
- 来源: https://aosabook.org/en/v1/bdb.html
- 阶段: Phase 1 · 2026-08-04

## 问题类
在**应用地址空间内**提供可靠、可事务、多访问方法的嵌入式数据管理（非独立数据库服务器）。

## 硬约束
- 库形态链接进应用；API 边界长期稳定
- 事务、恢复、（后来）复制必须可演进
- Unix「做一件事做好」的模块哲学

## 机制（共性）
1. **访问方法与存储服务分离**（Btree/Hash/… vs Mpool/Lock/Log/Txn）
2. **子系统级 API 边界**；多实现可替换（Lampson：面向对象=API 后多实现）
3. **WAL + 恢复基础设施**统一化（非各访问方法手写恢复）
4. **先写完整手册/设计再写代码**（Design Lesson 2）
5. 新能力（复制、SQL）尽量经既有 API 接入，避免推倒重来

## 策略（差异/选项）
| 策略 | 说明 |
|------|------|
| 嵌入式库 vs 独立服务器 | 牺牲独立运维模型，换入进程延迟与部署简单 |
| 子系统同步 vs 早期进程管理器方案 | 演进中的并发策略 |
| 日志游标化（复制压力下） | 单「当前日志指针」抽象不够时升级 |

## 显式模式名
- Layers（访问方法 / 缓冲 / 锁 / 日志 / 事务）
- Strategy（多访问方法同一 handle API）
- Write-Ahead Logging

## 决策与负面后果
- 二十年演进导致模块与交叉 API 膨胀——架构会老化，边界必须守护
- 恢复子系统实际比设计图更重（现实 vs 意图）

## 对写作规范的启示
- **Design Lessons** 一等公民 = M8 学习痕迹
- 展示「意图架构 vs 实际架构」图——诚实写演进
