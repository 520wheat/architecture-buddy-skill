## 问题类
构建**可复用的低级工具链组件库**（汇编器、编译器、调试器等），而非单体编译器可执行文件；同时服务静态编译与 JIT/运行时编译，并在多语言×多目标间摊薄优化器成本。

## 硬约束 / 历史对照
- 当时开源语言实现多为专用单体工具，前端难复用于分析/重构
- 社区常分裂为「静态编译」vs「解释/JIT」，共享极少
- 经典三阶段（前端/优化/后端）教科书模型在实践中很少真正落地

## 机制（共性）
1. **可复用库 + 清晰接口**（从 Day 1）
2. **LLVM IR 作为一等公民语言**：文本 / 内存 / bitcode 三种同构形态
3. **优化器面向 IR**：与源语言和目标机解耦的「完美世界」
4. **经典三阶段实现真正的 M×N 复用**：新语言写前端，新目标写后端
5. Pass 管线：找模式 → 证明安全 → 变换

## 策略（差异/选项）— 相对 GCC / JVM / 译到 C
| 策略 | 收益 | 代价 |
|------|------|------|
| LLVM 库式 IR 中心 | 可嵌入、可 JIT、可拆件；静态+运行时共享 | IR 设计极难（既要好生成又要够表达） |
| JVM/.NET 字节码+固定运行时 | 多语言共享 JIT/GC | 强制对象模型/GC，不适合 C 等 |
| 源→C→现有 C 编译器 | 前端简单 | 异常/调试/尾调用等受损 |
| GCC 多前端多后端但单体 | 社区与优化质量 | 全局状态、泄漏抽象、难当库嵌入 |

## 显式模式名
- Pipes and Filters / Pass pipeline（优化）
- Layers（前端 / IR 优化 / 后端）
- Facade/Library API（相对单体 CLI）
- Intermediate Language as Integration Hub

## 决策与负面后果
- 「没有真正好的子系统——都重写过至少一次」：库边界允许演进
- GCC 的失败模式（层泄漏、全局状态）作为反面教材写进架构叙事
