# OWASP ASVS 4.0 — V1 Architecture, Design and Threat Modeling
- 域: D7 安全架构
- 来源: https://asvs.dev/v4.0.3/V1-Architecture/
- 阶段: Phase 1 · 2026-08-05

## 问题类
如何用**可验证要求**约束应用安全架构：不是唯一实现答案，而是一组必须满足的架构属性与检查点（威胁建模、信任边界、集中化安全控制等）。

## 硬约束 / 立场（文档开篇）
- 「架构不是实现，而是对问题多种答案的思考方式；不存在单一正确实现」
- 安全架构应可复用、可随需求替换底层方案（例：统一 IdP 可演进 MFA）
- DevSecOps 时代仍需架构原则；左移到故事/设计/构建全程

## 机制（共性）— 从控制目标抽取
1. **威胁建模进入每次设计变更/冲刺**（1.1.2）
2. **文档化信任边界、组件与重要数据流**（1.1.4）
3. **集中、简单、经审查、可复用的安全控制**（1.1.6）——避免复制粘贴式安全
4. **执行点在可信层**：访问控制/校验不在不可信客户端（1.4.1, 1.5.3）
5. **单一认证/授权机制**且全路径同等强度（1.2.3–1.2.4, 1.4.4）
6. **数据分级 → 保护要求映射进架构**（1.8.x）
7. **组件间通信认证与加密**（1.2.2, 1.9.x）
8. **不同信任级别组件隔离**（1.14.1, 1.14.5）

## 策略（差异/选项）
| 主题 | ASVS 指向的策略空间 |
|------|---------------------|
| 身份 | 可扩展的单一认证机制（联邦等）vs 多套强弱不一入口 |
| 授权 | 网关/可信服务强制 vs 客户端强制（禁止） |
| 密码学 | 密钥生命周期与 vault；客户端密钥不可用于保护敏感数据 |
| 配置隔离 | 网关/代理/安全组/容器隔离等实现手段可选，要求是隔离本身 |

## 与 NIST ZTA / SAMM 对照
- ZTA：零信任原则与逻辑组件（问题类假设）
- SAMM：组织如何长出安全架构能力
- ASVS：**具体可验证清单**——三者互补，均不可互相替代
