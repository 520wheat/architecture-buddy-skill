# ADR-0009: 调研与 skill 纳入设计/架构模式（Patterns）canon

## Status

Accepted

## Context

机制骨架 v0.1（M1–M8）已确认。继续做「顶尖可学习的架构设计」样本调研时，需要纳入计算机软件发展中沉淀的 **设计模式 / 架构模式**：它们是对反复出现的问题的命名解法，是传统开发留下的可学习经验，不应被排除在架构探讨之外。

需避免两种偏差：

1. 把模式当成模块清单或面试背诵表（滑向实现细节堆砌）
2. 只谈抽象原则、完全不连结已被命名的解法（浪费公共知识资产）

## Decision

1. 公开 canon 调研范围扩展为：**架构描述/决策方法** + **模式文献（含设计模式与架构模式）** + **优秀架构描述样本**。
2. 在 Architecture Buddy 中，模式主要落在：
   - **M5 解决方案策略**：作为「机制/策略」的候选命名与对照物
   - **M6 决策与理由**：选用/排除某模式时要有 Context 与 Consequences
   - **M8 证据**：模式文献与 Top N 样本互相印证
3. 区分层次，避免混谈：
   - **架构模式 / 企业应用模式 / 集成模式**：优先用于问题类级抽象
   - **GoF 等细粒度设计模式**：在边界与机制已清后，作为局部策略或实现层附录，不默认占据架构笔记主结构
4. 使用方式符合伙伴身份：并列可选模式与适用条件，不背书「必须用某模式」。

## Consequences

- `03a` 调研增加 Patterns 专节；样本校准同时看「优秀架构如何引用模式」。
- §3 定稿时，策略选项表应能自然写入模式名、适用条件与代价。
- 构建期蒸馏架构师视角时，可关注其如何使用/批判模式，而非仅收集口号。
